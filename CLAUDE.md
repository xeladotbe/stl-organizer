# CLAUDE.md

Context for Claude Code (or any future contributor) working on this repository, so it doesn't need to be re-derived from scratch.

## What this is

stl-organizer is a Windows-first Electron desktop app for organizing 3D-printing model files (`.stl`, `.3mf`, `.obj`) that a hobbyist has scattered across their disk. Core value: rediscover forgotten downloads, spot exact duplicates, and browse via real 3D previews instead of cryptic filenames.

## Stack

Electron + React 19 + TypeScript, scaffolded via `electron-vite`. Tailwind v4 (via `@tailwindcss/vite`, no PostCSS config needed). Zustand for renderer state. `better-sqlite3` for the local library database. `three.js` + `@react-three/fiber`/`drei` for 3D rendering. `chokidar` for filesystem watching. `@tanstack/react-virtual` for row virtualization in the list/grid views. `@floating-ui/react` for scroll-aware context/kebab menus. `radix-ui` for accessible dialog/select/toggle/tabs primitives. `vitest` for unit tests.

## Contribution workflow

As of the v0.0.1 release, every change goes through: **GitHub issue → feature branch → implementation with unit tests → pull request → user approval → merge.** No direct commits to `main` for feature work. `gh` (GitHub CLI) is installed for creating issues/PRs from the terminal; it authenticates per-user via `gh auth login` (interactive), not something a session can do unattended. `.github/workflows/ci.yml` runs `typecheck`/`lint`/`test` on every PR and push to `main` — treat a red check as blocking before asking for approval. `.github/workflows/release.yml` is separate: it only builds installers and publishes a GitHub Release when a `v*` tag is pushed (see the Release section below), unrelated to the per-PR CI checks.

## Testing

`vitest` (config: `vitest.config.ts`, same `@shared`/`@renderer` path aliases as the app). Test files live next to the code they cover as `*.test.ts`/`*.test.tsx` (e.g. `src/renderer/src/lib/format.test.ts`, `src/renderer/src/components/ChipComboBox.test.tsx`). Run with `npm run test` (single run, used in CI) or `npm run test:watch`. Two kinds of coverage exist:

- **Pure, dependency-free logic** (`formatSize`, `toDisplayItems`, `isModelFile`, `parseSearchQuery`, `buildComboOptions`, …) — plain `*.test.ts` files, no rendering involved.
- **React components** — `*.test.tsx` files using `@testing-library/react` + `@testing-library/user-event`. Covers components that are reasonably self-contained to render and interact with (dialogs, pickers, `ChipComboBox`). Deliberately **not** covered: anything relying on WebGL/Canvas via `react-three-fiber` (`ModelPreview`) or on real browser layout/virtualization measurements (`FileTable`/`FileGrid`'s `@tanstack/react-virtual` usage, `ItemMenu`'s floating-ui positioning) — jsdom has no real layout engine, so these stay manually verified in the running app instead of chasing brittle, low-signal tests.

The whole suite runs under a single global `environment: 'jsdom'` (not per-file switching via `environmentMatchGlobs`) — mixing environments within one run left `@testing-library/user-event` with a stale `globalThis.document` captured from whichever environment its module graph first loaded under, breaking it for every component test. jsdom is a superset of plain `node` globals, so this doesn't affect the pure-logic tests. `vitest.setup.ts` registers `afterEach(cleanup)` explicitly (this project doesn't enable vitest's `globals: true`, so React Testing Library's usual auto-cleanup detection doesn't kick in on its own) and stubs a few browser APIs jsdom doesn't implement but Radix UI's pointer-based interactions call (`hasPointerCapture`/`setPointerCapture`/`releasePointerCapture`, `scrollIntoView`, `ResizeObserver`) — without these, tests touching Radix `Select`/`Dialog`/`AlertDialog` throw "not a function" errors unrelated to the behavior under test.

Nothing exercises `better-sqlite3` repositories or Electron/IPC yet. If a future feature needs DB-layer tests, prefer a real in-memory `better-sqlite3(':memory:')` instance running the actual migrations over mocking the DB — this project doesn't mock its own persistence layer anywhere else.

## Architecture

- `src/main/` — Electron main process (Node context)
  - `db/` — SQLite schema (`migrations.ts`, numbered migrations applied idempotently), repositories per entity (`filesRepo`, `foldersRepo`, `tagsRepo`, `categoriesRepo`, `modelGroupsRepo`)
  - `watcher/watcherManager.ts` — one `chokidar` watcher per watched folder; the initial `ready` scan doubles as the recursive first pass
  - `scanning/scanner.ts` — turns a raw fs path into a DB upsert (extension filter, stat, upsert)
  - `hashing/` — streaming sha256 (`hasher.ts`) + a concurrency-limited sweep queue (`hashQueue.ts`, `CONCURRENCY=3`, no worker_threads — deliberate simplification)
  - `thumbnails/` — `thumbnailWindow.ts` manages a **hidden** second `BrowserWindow` (vanilla three.js, not React) that renders one model to PNG per job over IPC; `thumbnailQueue.ts` orchestrates which file gets rendered next and writes the PNG to `userData/thumbnails/<hash-or-file-id>.png`
  - `settingsWindow.ts` — a **visible**, singleton third `BrowserWindow` (reuses the main preload, own `settings.html`/`SettingsApp.tsx` renderer entry) for managing watched folders, opened via the main window's gear icon
  - `priorityQueue.ts` — holds the current "visible on screen" file ids so hash/thumbnail sweeps process those first (see Renderer below)
  - `protocol.ts` — registers the custom `stl-file://` scheme used to stream local file bytes (and cached thumbnails) into the renderer's three.js loaders / `<img>` tags without CSP/`file://` friction, plus `hdri-file://` for user-picked HDRI files outside the watched library (see "Model preview: HDRI environment lighting" below)
  - `ipc/` — one file per IPC "namespace" (`filesIpc`, `foldersIpc`, `tagsIpc`, `categoriesIpc`, `duplicatesIpc`, `modelGroupsIpc`, `appIpc`), registered from `ipc/index.ts`, which also forwards main-process events to the renderer
  - `appEvents.ts` — shared `EventEmitter` so watcher/hasher/thumbnailer can all notify the IPC layer without circular imports
- `src/preload/` — two separate preload scripts: `index.ts` (main window **and** the settings window share this, full `window.api` surface) and `thumbnail.ts` (hidden thumbnail window, minimal `window.thumbnailApi`). Both are separate electron-vite build entries (see `electron.vite.config.ts`).
- `src/renderer/` — three separate HTML/entry pairs, also separate build entries: `index.html`/`src/main.tsx` (the real app), `thumbnail.html`/`src/thumbnail-entry.ts` (vanilla three.js, no React, hidden window), `settings.html`/`src/settings-main.tsx` (small standalone React page, no Zustand store — talks to `window.api.folders.*` directly)
  - `src/renderer/src/store/useLibraryStore.ts` — single Zustand store for all renderer state (files, folders, tags, categories, groups, `selection` — a `{type:'file'|'group', id}` union, since either a file or a model group can be selected — `selectedFileIds` + `selectionAnchorId` for shift/ctrl-click multi-select, see below)
  - `src/renderer/src/components/` — `FileList` (container: search bar with `tag:`/`category:` token syntax, list-vs-grid toggle), `FileTable` (virtualized, sortable + resizable-column list view), `FileGrid` (virtualized thumbnail card grid, model groups render as regular tiles with a 2×2 thumbnail mosaic), `DetailPane` (live 3D preview, inline rename, tag/category pickers with inline "create new", model-group membership editor with per-file remove/delete), `ModelPreview` (the `@react-three/fiber` viewer, geometry decoded off-thread — see below), `ItemMenu` (scroll-aware right-click/kebab context menu, see below), `GroupNameDialog` (small modal for naming a new model group), `DuplicatesView`. No sidebar — folder management moved to the settings window, tag/category management moved into `DetailPane`.
  - `src/renderer/src/lib/groupFiles.ts` — turns the flat, already-filtered `FileRow[]` into `DisplayItem[]` (lone files vs. collapsed model-group entries) for `FileTable`/`FileGrid` to render
  - `src/renderer/src/hooks/useVisibilityPriority.ts` — `IntersectionObserver`-based hook reporting on-screen file ids to the main process
  - `src/renderer/src/hooks/useModelParts.ts` + `src/renderer/src/workers/modelParser.worker.ts` — offloads STL/3MF/OBJ fetch+decode to a dedicated Worker for the live preview, see below
- `src/shared/` — types/helpers usable from both main and renderer (`types.ts` for all IPC wire-format types, `modelFileUrl.ts` for the `stl-file://` URL builders). Renderer imports these via the `@shared` alias; main/preload use relative paths (the renderer's tsconfig doesn't include `src/main`, so keeping wire-format types here avoids cross-tsconfig type leakage).

## Model groups ("virtual files")

Many multi-part prints get exported as several separate STL files that logically belong to one model. `model_groups` (migration 2) lets the user bundle several `files` rows under one named group (`files.group_id`) — purely a browsing/organizing construct, not a merge: hashing, thumbnails, and duplicate detection all stay entirely file-level and are untouched by grouping. Grouping is a **client-side presentational layer** (`groupFiles.ts`) over the already-filtered flat file list, not a SQL-level concept — this keeps the search/sort/virtualization code from having to know groups exist. Tags stay per-file even for grouped files (a collapsed group card shows the union of its members' tags as read-only); categories can be set on the group itself.

A group with ≤1 member left auto-dissolves — two separate code paths reach this, both in `modelGroupsRepo.ts`: `removeFileFromGroup` (explicit "remove from group" action) and `dissolveGroupIfSparse` (called from `files:moveToTrash` in `filesIpc.ts` after a grouped file is trashed). The latter deliberately does **not** clear `group_id` on the trashed file itself, only on whoever's left — so restoring the file from the Recycle Bin puts it back in its group instead of leaving it permanently orphaned.

## Selection model (shift/ctrl-click, no "mode" toggle)

`selectedFileIds` + `selectionAnchorId` in the store drive standard file-explorer-style multi-select — there's no separate "selection mode" to switch into. A plain click on a file always collapses the selection down to just that file (see `selectFile`); ctrl-click toggles one file in/out via `toggleFileSelection`; shift-click selects the contiguous range from `selectionAnchorId` to the clicked file via `selectFileRange`, using the **currently displayed order** (`FileTable`/`FileGrid` each build their own `orderedFileIds` from what's actually rendered, respecting sort/filter/expand state). Right-clicking (or the ⋮ button in grid view) a file that's part of the current multi-selection opens a menu acting on the whole selection (`Group…` / `Delete (N)`); right-clicking outside the selection collapses it to just that file first, matching Explorer/Finder — via **`collapseSelectionTo`**, not `selectFile`: it updates `selectedFileIds`/`selectionAnchorId` (so the file reads as selected and the menu acts on the right target) without touching `selection`, which is what opens the detail pane/live preview. Only a plain left-click is allowed to open the detail pane. `Group…` opens `GroupNameDialog` rather than an inline toolbar input.

## Model preview: off-main-thread parsing

Fetching + decoding an STL/3MF/OBJ (`STLLoader`/`ThreeMFLoader`/`OBJLoader` from `three/addons`) is synchronous, CPU-heavy work — doing it on the renderer's main thread froze the whole app's UI for large files. `src/renderer/src/workers/modelParser.worker.ts` does the fetch and decode inside a dedicated Worker (built via Vite's `?worker` import), posting back only the resulting `Float32Array`s (position/normal/color, transferred zero-copy) plus a per-part material color; `useModelParts.ts` reassembles them into `THREE.BufferGeometry` on the main thread, which is cheap. The worker's tsconfig can't declare `lib: ["webworker"]` (this project's renderer code shares one DOM-lib tsconfig, and DOM + WebWorker ambient globals can't coexist in one TS program) — the worker file casts `self` to a minimal hand-written shape instead of relying on ambient `WorkerGlobalScope` types.

`OBJLoader.parse()` takes a decoded **string** (OBJ is a plain-text format), unlike `STLLoader.parse()`/`ThreeMFLoader.parse()` which take an `ArrayBuffer` — the worker branches on `ext` to call `response.text()` vs `response.arrayBuffer()` before parsing accordingly. `ThreeMFLoader` and `OBJLoader` both return a multi-mesh `Object3D`/`Group` (one child per part/named object) that gets `traverse()`d for meshes, whereas `STLLoader` parses directly to a single `BufferGeometry` — see `extractPartsFromObject()` vs the plain-STL branch in the worker.

`ThreeMFLoader.parse()` calls `new DOMParser()` internally to read the 3MF's embedded XML — `DOMParser` is a Window-only API that doesn't exist in a dedicated Worker's global scope, so without a polyfill every `.3mf` file fails with "DOMParser is not defined" (STL/OBJ don't hit this, neither loader parses XML). Fixed by importing `DOMParser` from `linkedom/worker` (a pure-JS DOM implementation with no Node built-ins, so it actually works inside a real non-Node-integrated Worker) and assigning it onto the worker's `self` before the loader runs; its `querySelector`/`querySelectorAll` support the descendant-combinator selectors (`'vertices vertex'`, etc.) `ThreeMFLoader` relies on. Regression-tested in `modelParser.worker.test.ts` by building a minimal in-memory 3MF archive (via `fflate`'s `zipSync`) and parsing it with the real `DOMParser` global removed.

Fixing the DOMParser crash surfaced a second, previously-masked bug: 3MF `<item>`/`<component>` elements can carry their own `transform` (position/rotation/scale), which `ThreeMFLoader` applies to each mesh's `position`/`quaternion`/`scale` — **not** to the geometry's vertex data. `extractPartsFromObject()` was reading `mesh.geometry` directly, silently dropping every one of those transforms, so multi-part 3MF models rendered with all parts collapsed on top of each other at the origin instead of assembled correctly (STL is single-part and OBJ has no transform concept, so neither format ever hit this). Fixed by calling `object.updateWorldMatrix(true, true)` (both arguments matter — `updateChildren=false` leaves descendant `matrixWorld`s stale/identity) and baking each mesh's `matrixWorld` into a cloned copy of its geometry (`mesh.geometry.clone().applyMatrix4(mesh.matrixWorld)`) before extracting the position/normal arrays.

A third bug, the one actually responsible for 3MF models rendering as a garbled/holey mesh even without any per-part transform: **3MF meshes are indexed by default** (`ThreeMFLoader`'s `buildDefaultMesh()` produces a unique vertex list plus a separate triangle `index`, unlike STL which is always non-indexed). `extractPart()` only ever read `position`/`normal`/`color` off the geometry, silently dropping `geometry.index` — the reconstructed geometry on the main thread then had no choice but to treat every 3 consecutive *vertices* as one triangle, producing wrong connectivity wherever a vertex is shared between triangles (i.e. almost always, for any real mesh). Fixed by adding `index: Uint32Array | Uint16Array | null` to `PartPayload`, transferring `geometry.index.array` alongside the other typed arrays, and calling `geometry.setIndex(...)` when reassembling in `useModelParts.ts`.

A fourth bug (#36), found after all three above: a **mirrored** per-part transform (negative-determinant `matrixWorld` — e.g. a 3MF `<item>`/`<component>` with a -1 scale on one axis) correctly flips vertex positions via `applyMatrix4`, but leaves each triangle's winding order exactly as authored. Three.js normally compensates for a mirrored mesh by flipping the GL front-face convention it expects at render time — but it keys that off the *rendered mesh's own* `matrixWorld` determinant (`object.matrixWorld.determinantAffine() < 0` in `WebGLRenderer.renderBufferDirect`), and here the mirror is baked into the geometry ahead of time while the `<mesh>` itself renders with an identity transform, so that compensation never fires. The mirrored part's faces then read as back-facing under the default front-face winding convention and get backface-culled, showing through to whatever's behind them instead of the actual surface — reported as a hole/opening rendering as solid, or vice versa, depending on what happens to be behind. Fixed by `reverseWindingOrder()` in `modelParser.worker.ts`: when `mesh.matrixWorld.determinant() < 0`, swap the second and third vertex/index of every triangle after baking the transform in, restoring a winding order consistent with the mirrored positions. Regression-tested with a build item using transform `"-1 0 0 0 1 0 0 0 1 0 0 0"` (mirror across X).

`@react-three/drei`'s `<Bounds fit clip observe>` auto-fits the camera **once, on `<Canvas>` mount** — not when content actually appears. Since geometry now arrives asynchronously (worker round-trip), that auto-fit runs against an empty scene and frames a meaningless default box, leaving the model comically mis-scaled until something else happened to force a refit. Fixed by calling `useBounds().refresh().fit().clip()` manually from inside the mesh-rendering component, in a `useEffect` keyed on the parsed data actually becoming available (see `ParsedModel` in `ModelPreview.tsx`). If you add more async-loaded content inside a drei `Bounds`, you'll need the same manual trigger.

## Model preview: HDRI environment lighting

`ModelPreview` can light the scene from a user-picked local HDRI (`.hdr`/`.exr`) instead of the default ambient+directional lights, via drei's `<Environment files={...}>`. The picked file lives anywhere on disk (not inside a watched folder), so it can't use the id-based `stl-file://` scheme — a second custom protocol, `hdri-file://` (`src/shared/hdriFileUrl.ts`, handler in `src/main/protocol.ts`), opaque-encodes the whole absolute path as the URL's path segment rather than trying to parse it as a real file:// path (drive letters/backslashes don't round-trip through URL parsing otherwise). This only works because `encodeURIComponent` never escapes letters or dots, so the URL's tail still literally ends in `.hdr`/`.exr` — required for drei's `useEnvironment` to sniff the format via `url.split('.').pop()`. The picked path is persisted in `localStorage` (`useLibraryStore`'s `hdriPath`/`pickHdri`/`clearHdri`), not the SQLite DB — it's a display preference, not library data, and there's no settings/key-value table to put it in yet.

`<Environment>` loads via drei's Suspense-based `useLoader` cache, so it needs its own `<Suspense>` — and its own error boundary (`HdriErrorBoundary`, distinct from `ModelErrorBoundary`): a bad/missing HDRI file should fall back to the default lighting rig, not hide the whole model behind "Preview unavailable". Its `componentDidCatch` calls `useLibraryStore.getState().clearHdri()` directly (no hook needed, since it's a class component reacting to a render-time error, not rendering reactively) — clearing `hdriPath` makes `ModelPreview` re-render onto the default-lighting branch instead of retrying the same broken URL forever.

## Scroll-aware context menus

`ItemMenu.tsx` (right-click menus in `FileTable`, right-click + ⋮ button in `FileGrid`) uses `@floating-ui/react` rather than hand-rolled scroll-position math (an earlier version did that — bugs included the menu lagging/sticking during virtualized scroll and floating over the sticky column header or the search bar). The reference is a **virtual element**: `getBoundingClientRect()` is recomputed from the anchor row/card's *live* position plus a fixed click offset every time `autoUpdate` asks for it, and `contextElement` is set to the real anchor DOM node — without `contextElement`, floating-ui has no real element to attach scroll/resize observers to and won't track anything. The `hide()` middleware's `referenceHidden` flag closes the menu once the anchor scrolls out of its clipping container; `FileTable` additionally passes a `topPadding` (measured from the sticky `<thead>`'s height) since a sticky header covers part of the scroll container without actually clipping it, which `hide()` can't know about on its own.

The `ref={refs.setFloating}` callback (floating-ui's documented API) trips the newer `react-hooks/refs` ESLint rule, which can't distinguish a third-party ref-setter function from a raw `.current` read — suppressed with a scoped `eslint-disable-next-line`, not a config-wide override, since it's specific to this one line's shape.

Closing on outside click/right-click/Escape uses floating-ui's `useDismiss` + `useInteractions` rather than hand-rolled `window.addEventListener('click'/'contextmenu'/'keydown', ...)` (an earlier version did that, deferred via a `setTimeout(0)` to avoid the same event that opened the menu also closing it — but that delay left a real window right after the menu opened where a fast outside click was silently dropped instead of dismissing it, reported as issue #19). `useDismiss` attaches its listener synchronously (no artificial delay) and correctly recognizes clicks on the menu itself as "inside" via the reference/floating elements it already knows about — including the virtual reference element, since `contextElement` is set. `useDismiss` has no "window blur" dismiss type, so a small manual `window.addEventListener('blur', onClose)` stays alongside it for that one case (e.g. alt-tabbing away while the menu is open). Regression-tested in `ItemMenu.test.tsx` by firing a synchronous outside click right after mount, with no `await`/timer flush — this reproduces the dead window the old `setTimeout(0)` version had. Not tested there: "clicking inside doesn't close it" — jsdom's lack of real hit-testing made `userEvent.click()`'s synthetic pointer events resolve `composedPath()` differently than a real browser click would for an element that was never actually laid out.

## List/grid virtualization

Both `FileTable` and `FileGrid` use `@tanstack/react-virtual` to stay fast on libraries with thousands of files. `FileTable` keeps a real `<table>` (required for the `colgroup`-based resizable columns) and virtualizes via the "two padding `<tr>` rows" technique rather than absolute positioning, since absolutely-positioned `<tr>`s break table layout. `FileGrid` computes its own responsive column count from the scroll container's measured width (mirroring what CSS `repeat(auto-fill, minmax(...))` would do) and virtualizes by row, with **explicit pixel `cardWidth`** computed in JS rather than per-row CSS Grid `1fr` — needed because, in an earlier version where group tiles rendered as an indented nested grid, that row's independently-resolved `1fr` produced visibly mismatched card widths. (Group tiles are now regular same-width grid cells, not indented, but the JS-computed width stayed since it's the more robust approach.)

## Data pipeline (per file)

1. **Scan**: chokidar detects a `.stl`/`.3mf`/`.obj` file → `scanner.ts` upserts a `files` row (`hash_status`/`thumbnail_status` both start `'pending'`).
2. **Hash**: `hashQueue.ts` only hashes files that **share their exact size with another file** (a uniquely-sized file can never be an exact duplicate — pure optimization for dedup detection). This means a large fraction of any real library never gets hashed, by design.
3. **Duplicates**: derived on demand from `content_hash` (`listDuplicateFiles`), not stored — always current, no separate table to keep in sync.
4. **Thumbnail**: `thumbnailQueue.ts` picks any file with `thumbnail_status='pending'`, **independent of hash status** (this was a real bug once — see Gotchas). If the file has a `content_hash` and another file with that hash already has a thumbnail, it's reused (dedup); otherwise the hidden window renders a fresh PNG, keyed by `content_hash` if available or `file-<id>` if not.
5. **Priority**: whatever `useVisibilityPriority` reports as on-screen gets processed first in both the hash and thumbnail sweeps; everything else is still worked through in the background regardless (never starves).

## Gotchas already hit — don't reintroduce these

- **Never use a bare numeric string as a custom-protocol hostname on a `standard: true` Electron scheme.** Chromium's URL parser reinterprets an all-digit host as an IPv4 address and silently rewrites it (`stl-file://3812/...` → `stl-file://0.0.14.228/...`), breaking any id-based lookup. Fix in place: prefix with a letter (`f${id}`) — see `src/shared/modelFileUrl.ts`.
- **Dispose three.js resources between jobs in the hidden thumbnail window.** It's a single long-lived WebGL context processing thousands of jobs; without explicit `geometry.dispose()`/`material.dispose()`/texture disposal after each render, GPU memory leaks until the context is lost and every subsequent render silently fails. See `clearModel()` in `thumbnail-entry.ts`.
- **`hash_status='hashing'` / `thumbnail_status='rendering'` can only ever be a leftover from an abrupt shutdown** — there's no in-process recovery otherwise. `resetStuckProcessingStatuses()` runs on every startup for exactly this reason; don't remove it.
- **Thumbnail eligibility must never depend on hash completion.** They look related (thumbnails dedupe via `content_hash`) but are separate concerns — gating thumbnails on `hash_status='done'` silently excludes every uniquely-sized file from ever getting a preview, which was most of a real user's library.
- **The render timeout in `thumbnailWindow.ts` needs headroom for real-world file sizes** (STL/3MF/OBJ files run into the hundreds of MB); too short a timeout misclassifies slow-but-valid files as `'unsupported'`.
- `ELECTRON_RUN_AS_NODE=1` may be set in the ambient dev shell — if `npm run dev` throws `Cannot read properties of undefined (reading 'isPackaged')`, unset it before relaunching.
- **Renaming a file must update the DB row's path *after* the on-disk `fs.rename`, not before, and the watcher event race is what makes the order matter.** `files:rename` in `filesIpc.ts` renames on disk first, then updates the row synchronously right after — by the time chokidar's debounced `add` fires for the new path (~1.5s later, via `awaitWriteFinish`), the row already matches it, so `upsertFile`'s existing-row branch applies and hash/thumbnail state survives untouched instead of the file looking "re-added" from scratch.
- **Stray `electron.exe` processes accumulate across dev-server restarts on Windows.** Stopping the `npm run dev` background task only kills the `npm`/node wrapper, not the spawned Electron process tree — leftover instances fight over the same userData dir (`Unable to move the cache: Zugriff verweigert`) and can each independently run watcher/hash/thumbnail sweeps. Check `tasklist /FI "IMAGENAME eq electron.exe"` and `taskkill /F /IM electron.exe` before a clean restart if `npm run dev` logs cache-access errors on startup.
- **Don't give an absolutely-positioned virtualized row its own independent CSS Grid `1fr` track sizing if a sibling row has different available width** — each row resolves `1fr` against its own container independently, so visually "identical" cards can end up different widths. Compute pixel widths in JS instead (see `FileGrid.tsx`'s `computeLayout`).
- **`@react-three/drei`'s `<Bounds fit observe>` only auto-fits on `<Canvas>` mount, not when async-loaded content appears.** If geometry loads after mount (e.g. from a Worker), call `useBounds().refresh().fit().clip()` manually once it's actually in the scene — see the Model preview section above.
- **A `@floating-ui/react` virtual element needs `contextElement` set to a real DOM node**, or `autoUpdate` has nothing to attach scroll/resize observers to and the floating element won't track anything. See `ItemMenu.tsx`.
- **This renderer's tsconfig can't add the `webworker` TS lib** (it'd conflict with the DOM lib the rest of the renderer needs) — worker files type `self` via a hand-written cast instead of relying on ambient `WorkerGlobalScope` globals. See `modelParser.worker.ts`.

## Status vs. plan

M1–M5 all implemented: watched folders, exact-duplicate detection + Recycle Bin cleanup (`shell.trashItem`, never permanent delete), STL/3MF thumbnails + live 3D preview, tags/categories with filtering, list/grid views with sortable + resizable columns, visible-first background rendering priority. Since then: file rename (on-disk + DB), model groups/"virtual files" for multi-part prints (including per-file delete from within a group), list/grid virtualization for large libraries, search extended to `tag:`/`category:`/`type:` tokens plus group-name matching, a dedicated settings window for watched-folder management (sidebar removed), inline tag/category creation from the detail pane, Explorer-style shift/ctrl-click multi-select with right-click Group/Delete, off-main-thread model preview parsing, scroll-aware context menus, and `.obj` support alongside STL/3MF. Not yet done: worker_threads for hashing (intentionally skipped as unnecessary complexity), corrupt-file UX polish beyond the basic unsupported-placeholder, packaging/signing pass, STEP file support (tracked separately — needs a CAD-kernel dependency, a much bigger lift than the mesh formats).
